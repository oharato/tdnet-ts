# tdnet-ts 改善計画：取得の信頼性と段階的な開示検索

作成・更新日: 2026-10-24。状態: 計画と実装進捗。完了範囲は直下の進捗欄を参照し、それ以外は未実装。検索機能への追加希望を反映し、初版の「小保守後は保守中心」という結論を改訂した。

## 実装進捗（計画作成後の追記）

最初の実装は、4.3と第1段階の共通条件に当たるJST日付検索に限定した。今後の検索方式でも同じ企業・期間条件が必要であり、取得・モデルを動かさず境界を検証できるため、取得復旧とは独立した小さな変更として先行する。

- 実装: 日付のみの開始以上/翌日開始未満、時差付きISO日時のUTC正規化と終了境界包含、不正入力・逆転範囲の拒否。
- 互換性: 日付のみはUTC日からJST日に変更。明示的なUTC日時による範囲と既存キーワード/企業/タイトル/件数/新着順は維持。DB移行は不要。
- 検証: 架空データのメモリ内SQLiteで境界・うるう日・年越し・入力エラー・既存filterを確認。既存PDF fixtureを含むテスト、build、lintも実施。lintの既存警告は別件として維持。
- 本番取得・既存利用中DBの変更・追加依存・モデル導入・外部embedding送信・課金はなし。独立したテスト用CIを追加し、デプロイworkflowは変更しない。
- 残作業: 実例に基づく評価集合、AND/OR/フレーズ、表記揺れ/誤字、意味検索の採否、原本・再試行の復旧、Web時刻表示。以下の調査本文は計画時点の記録であり、「現状」「未実行」はその時点を指す。

### 検索の土台の実装進捗

日付境界の次に、第1段階の対象項目と複数語検索を実装した。既定をANDにする初期案は、既存の空白を含む検索・LIKEワイルドカードを壊さないよう見直し、従来動作を `legacy` として残して `literal` / `all` / `any` を明示選択する方式にした。

- 対象: CLI/ライブラリのtitle/body/company指定、AND/OR、引用符フレーズ、短語・記号の文字どおり検索、既存filter併用、同時刻ID順とoffset。AND/OR混在構文は対象外。
- FTSは未導入。今回の目的は検索の意味と正しさの確定であり、LIKEで日本語短語を扱える。性能計測なしに索引・モデルを増やさない。
- メモリDBの架空データで対象項目、NULL、空白、短語、引用符、SQL用記号、日付とORの併用、ページ境界を検証する。
- 後続: 実資料に基づく評価集合・関連度と根拠表示の拡充、Webへの反映、表記揺れ/誤字、意味検索の評価。取得復旧の残作業も独立に残す。

### 第2段階の最初の範囲：限定的な表記揺れ対応

任意の `normalize: 'width-case'` / `--normalize width-case` を追加した。全角ASCII・全角空白・ASCII大小だけを検索時に揃え、既存literal/legacyの既定結果を変えない。legacyとの併用は拒否する。広いNFKCではカナや互換記号も畳まれるため、まず原文位置を保てる限定変換を採用した。

- 比較対象と検索語を同じ規則で変換し、SQLのエスケープは変換後に行う。フレーズ構文は変換前に解析。原文とNULLは保持し、検索結果・抜粋は元の表記を返す。
- 新規14ケースで未対応ランタイムと全半角・会社名・短語・記号・引用句・AND/OR・JST日付・ページ分割・対象外変換・既定互換を試験DB/fixtureで検証。
- DB変更・再索引・追加依存・モデル・外部API・課金なし。接続内の関数による走査なので、大量データでの速度は未測定。
- 残り: 半角カナ等を広げるかの評価、誤字候補、実例に基づく検索評価、Web反映、意味検索の採否。これらは今回の実装に含めない。

### Web検索の接続

静的JSONとAlpine.jsの既存構造を確認し、別サーバーやSQLiteのブラウザ導入を避け、共有の検索語解析・日付境界・限定変換を使う小さなWeb検索を追加した。対象項目・literal/AND/OR・引用句・JST日付・銘柄・width-caseをフォームで選択する。未対応の誤字/意味検索をUIに追加しない。

- ページ変更/条件変更・戻る/進む・繰返し検索を扱う。本文と原本URLを維持し、本文欠損と読み込みエラーを区別する。Textの一致箇所を原文のまま強調する。
- WebとSQLiteの架空データ一致、UI状態の受入テストを追加。独立レビューで小画面のフォーム高さを指摘され、折畳み・スクロール・一覧領域確保を追加した。ブラウザ操作環境が未接続のため実画面QAは未実施。
- Webは出力済みJSONの範囲だけを検索する。性能・検索品質評価、カナ/誤字・意味検索、原本復旧は後続。モデル・外部API・依存・DB移行・本番取得・デプロイなし。

## 1. 結論

適時開示の一覧取得、PDFからの本文抽出、SQLite保存、検索、CLI、Web閲覧、RSSは既にある。追加希望の「キーワード検索・あいまい検索・ベクトル検索」には、既存の単純な部分一致を超える価値がある。**取得・復旧を支える保守と、欲しい開示を見つける検索改善を段階的に進める**計画とする。機能追加を一律に不要とはしない。

役割は「開示を保存して、知っている語で探す」から「言い回しが分からなくても関連する開示と根拠箇所を見つける」まで広がる。第1段階は対象項目・AND/OR・フレーズ・日付/企業条件、第2段階は表記揺れと誤字、第3段階は意味検索とキーワードの併用。第3段階を初手で必須にせず、評価用の開示例で改善を確かめて採否を決める。AI要約・投資判断・独自分類は別用途であり追加しない。

検索の前提には「失敗した資料を再処理できる」「指定した日本の日付で探せる」「検索できた範囲を誤解しない」ことがある。実際の欠落件数・検索精度・応答速度は未測定。本文保存済みの資料を活用し、未抽出本文を検索できるかのようには扱わない。全件の長期保存や訂正履歴の保証が必要なら、取得元を再検討する。

## 4. 取得用途として残る改善

### 4.1 最優先：失敗の可視化と再処理

`retryCount` が3になると、次回同期でも `retryCount <= roundIdx`（ラウンド番号0〜2）を満たさず処理対象にならない。対象資料が一覧に再登場しても復旧しない。さらに個別失敗を記録した後も `sync()` は正常終了し、CLIから成功・部分失敗を区別できない。これはコード上で確認した挙動であり、現存DBに該当レコードがあるかは未確認。

小さな改善として、成功・既存・失敗・対象外の件数を返すこと、失敗IDを指定して再処理できることを優先する。自動で無限再試行せず、過去の失敗回数と今回の試行回数を区別する。再処理対象が最新一覧から外れていてもDBの保存URLから復旧できる設計を検討する。

不正日時やコード欠落は、例外処理の中でも同じ変換を行っているため、1件の不正値が同期全体を中断させ得る。入力検証もこの段階に含める。CLIの `limit` やライブラリの `concurrency` は正の整数を要求する（特に並列数0ではループが進まない）。

### 4.2 原本の保存と本文抽出を分ける

現状は変換に失敗すると、ダウンロードできていても `--save-pdf` に原本を残せない。また、本文保存済みの資料に後から `--save-pdf` を付けてもスキップされる。PDF書込み失敗もログのみで、本文が保存されると次回はスキップされる。Webは常にローカルPDFリンクを作るため、この組合せではリンク先が欠け得る。

原本を残したい利用が続くなら、PDF取得・保存と本文抽出の成功状態を分ける。原本が保存済みなら再変換はそのファイルを使う。原本URLとIDは既にあるので維持し、最終取得時刻やファイル状態だけを必要最小限で追加する。内容の指紋（ハッシュ）や版履歴は監査・差替え検知の需要が確認できてからでよい。

### 4.3 日付とコードの意味を固定する

取得時のJST→UTC変換自体は既存テストがある。一方、`search --start/--end YYYY-MM-DD` はJSTの1日を表さず、Webの日付表示も `timeZone` 指定がなく閲覧端末の時差に依存する。

CLIの日付のみ指定はJSTの暦日と明記し、内部では開始以上・翌日開始未満のUTC範囲にする案を優先する。時刻・時差付きのライブラリ入力を許すなら別に定義し、既存利用者への変更点を明示する。例えば架空の `2026-10-01` の範囲は `2026-09-30T15:00:00Z` 以上、`2026-10-01T15:00:00Z` 未満となる。

銘柄コードは文字列で保持し、英字入り4文字を許す。末尾0除去は5文字形式と確認できる場合だけに限定する。現在の英字コードが必ず壊れるという指摘ではない。API資料は4文字コードを案内しているが、実応答の `company_code` の全形式は今回未取得なので、4文字末尾0・5文字・英字入りを合成データで検証する。

### 4.4 欠落・重複・訂正を保証しすぎない

- `recent` の件数上限を超えた日や、長期停止後の取りこぼしを埋める仕組みはない。平日18時の実行設定だけでは当日全件を保証できない。翌回で拾える場合もあるため、実際の欠落と断定しない。
- APIの `limit` は最大件数指定であり、ページ分割の仕様や `total_count` の厳密な意味は今回確認できていない。上限到達は「欠落の可能性」として知らせ、件数を増やすだけで完全取得と扱わない。
- 同期対象内の同一IDは1回処理するようにすれば、DBの重複行防止に加えて重複ダウンロードも減らせる。現在はキュー作成時に既存判定するため、同一応答に同じIDが複数あれば複数回処理し得る。
- 本文保存済みの同一IDは表題・URL等も更新されない。別PDF名の訂正資料は別IDとして保存され得るが、元資料との関連付けはない。
- 型・DBに削除状態や訂正履歴の項目はない。一覧から消えたことや404だけを削除と判断しない。保持期限や一時障害と区別できないためである。

まず取得範囲と未保証事項を文書化し、同一IDのメタデータ更新を小さく検討する。全件追跡・削除伝播・訂正資料の自動関連付けは、取得元が必要な情報を提供するか確認してから判断する。

### 4.5 再試行・待機の補強

既存の指数バックオフ（失敗のたびに待ち時間を増やす仕組み）は残す。一覧通信には時間上限を設け、429・一時的5xxの限定再試行と `Retry-After`（再試行まで待つ秒数等を示す応答）を検討する。404や入力不正を同じように繰り返さない。並列2件＋1秒待機は実装上の設定であり、提供元が許可したレートという意味ではない。

PDF変換の `Promise.race` は待ち時間を制限するだけで、変換本体を中止しない。成功時にもタイマーを解除していない。再試行で処理が重なる可能性があるため、タイマー解放と依存ライブラリの中止可否を確認する。PDFのダウンロード上限と変換上限はそれぞれに適用され、合計時間の上限ではない。

## 8. 検索改善の3段階

### 8.1 既存検索と新規要件の区別

更新時に `src/db.ts`、`src/cli.ts`、`web/index.html`、package.jsonと検索テストの有無を再確認した。

| 観点 | 現在 | 今回の改善対象 |
| --- | --- | --- |
| キーワードの対象 | DBはタイトル・保存済み本文・会社名のいずれか。Webは銘柄コードも含む | 全対象/タイトル/本文/会社名を明示選択。コードの完全一致は独立filter |
| 複数語・フレーズ | DB/Webとも入力全体を1つの部分文字列として扱う。検索式のAND/OR構文はない。CLIは最初の検索位置引数のみ参照 | 複数語AND/ORと引用符によるフレーズ指定。演算子の意味と優先順位を固定 |
| 絞込み | DBはコード完全一致、タイトル部分一致、期間、件数。会社名だけの独立filterなし。Webは優待filterが既定ON | 既存filterを保持し、企業・日付条件を全検索方式に共通適用。優待限定が有効なことを明示 |
| 順位・根拠 | DBは公開日時の降順。CLIは本文に同じ文字列があれば前後を抜粋。タイトル一致だけでは本文抜粋なし | 新着順/関連度順を選択し、当たった項目・原文抜粋・日時・企業・原本URLを表示 |
| あいまい・意味検索 | 専用処理、FTS索引、embeddingはない。本文変換の一部文字正規化とWebの小文字化はある | 検索用の正規化、任意の誤字候補、意味検索を別々に評価 |
| 検索できる範囲 | DB内とWeb出力内は異なる。Webは既定1000件。本文nullでもメタデータで該当し得る | 対象資料数・本文未抽出・索引未更新・出力範囲を表示。検索0件を開示不存在と説明しない |

現在のDB `LIKE` は `%` と `_` をワイルドカードとして扱い、Webの `includes` は文字そのものとして扱う。SQL値の別渡しは行われているが、この意味の違いは残る。通常検索では文字通りに扱う案を基本とし、記号・引用符・正規表現記号も評価する。端末のハイライトは検索語から直接正規表現を作るため、検索構文の導入時にはエスケープも点検する。

### 8.2 第1段階：キーワードを正しく組み合わせる

提案する最小仕様は、通常入力の複数語をAND、明示的ORを代替条件、引用符内を順序を保った連続文字列とすること。例えば `配当 増額` は選択対象の中に両方を含む資料、`増配 OR 復配` はどちらか、`"自己株式取得"` は正規化後も連続する語句を探す。ANDを同じ文書の別項目にまたがって満たしてよいかは、まず「全対象なら可」と仮定し、根拠を項目別に表示する。括弧・NOT・複雑な検索式は初回必須にしない。構文不正は説明を返し、別の意味に黙って解釈しない。

企業は名称一致と銘柄コード完全一致を分ける。企業・期間のfilterは候補を制限する条件であり、関連度の低さで除外条件を緩めない。既定の日付は4.3のJSTの暦日とする。取得済みデータに対するローカル検索を入口とし、検索のたびにPDFを取得しない。

**実装候補の比較（まだ選定していない）**：

| 方法 | 日本語で得られるもの・限界 | 依存・更新負担と判断 |
| --- | --- | --- |
| 正規化したLIKE/文字列検索 | 部分一致や2文字の「配当」を維持でき、AND/ORを組み立てられる。全走査になりやすく、語の重要度による順位は別設計 | 追加依存が最小。初期の比較基準にする。データ量と速度が十分ならこれで第1段階を満たしてよい |
| SQLite FTS5のtrigram | 3文字単位で部分一致を索引化。MATCHでは3文字未満が当たらない。誤字補正や意味検索ではない | 既存SQLiteを使えるが短語には別経路が必要。LIKEのESCAPE指定では索引が効かない制限もあり、記号の意味と性能を両方測る |
| 日本語の分かち書き＋FTS5 | 文を語に分けて語句検索・順位付けする。標準unicode61だけでは日本語の単語分割にならない。分割した語のフレーズと原文の連続一致は同一ではない | Sudachi等の辞書・処理系と更新管理が増える。企業名・複合語・「増配/配当増額」の評価で必要になった場合に比較 |

FTS5は全文検索用の索引で、AND/OR、フレーズ、列指定、BM25（語の頻度などから順位を付ける方法）、抜粋機能を備える。外部content表を使う場合も元データとの更新同期はアプリ側の責務。[SQLite FTS5公式仕様](https://sqlite.org/fts5.html)

日本語の分割・表記正規化の一次資料として [Sudachi](https://github.com/WorksApplications/Sudachi) を参照した。辞書と分割単位、正規化規則を持つが、Nodeプロジェクトへの導入方法は未選定。語の正規化を追加しただけで適時開示の検索精度が上がるとは断定しない。

ローカル確認：Node `v24.22.1` の組込みSQLite `3.53.4` で、メモリ内に架空の1文 `自己株式取得を実施します` を登録した。unicode61のMATCHは `自己株式取得` / `取得` とも0件、trigramは前者1件・後者0件だった。この環境でFTS5が使えることと短語制約を確認しただけで、速度・実資料の精度・CI環境の互換性は未検証。ファイルDB・ネット通信・追加依存は使っていない。

### 8.3 第2段階：あいまいさを3種類に分ける

- **部分一致**：`自己株式` で `自己株式取得` を探す。既にある機能であり、誤字に強い検索とは区別する。
- **表記揺れ**：全角/半角、英字大小、余分な空白などを検索用に揃える。NFKC（Unicode文字の互換表記を揃える規則）等を候補とし、検索側と索引側に同じ処理を適用する。原文は残す。かな/カナ、旧字体、略称、同義語の一律変換は意味を混同し得るため別の小さな辞書として評価する。`自社株買い` と `自己株式取得` は単なる文字幅の違いではない。
- **誤字**：`自己株式取徳` のような入力を候補訂正する。候補語への編集距離（何文字直すと一致するか）などを比較し、全文のすべてを無制限に曖昧一致させない。完全一致を優先し、拡張した語と理由を表示する。銘柄コード・日付・金額・割合は自動訂正しない。

正規化後の一致位置を元の本文へ対応付け、原文の抜粋が壊れないことを確認する。辞書に増配/減配を同義語として入れるような誤拡張を避ける。FTS5採用と誤字補正は別判断であり、trigramだけで誤字まで解決する計画にはしない。

### 8.4 第3段階：意味が近い開示を見つける

ベクトル検索は、文章を数値の並び（embedding）に変えて意味の近さで候補を探す方法。例えば `株主への還元を増やす発表` から、同じ文言を使わない増配や自己株式取得の開示を候補にする。事実の真偽や投資価値の判定ではなく、原本を読む入口とする。

長いPDF本文を1本のベクトルに押し込まず、見出しや段落を保った小片に分ける。タイトル・会社情報を添え、原文位置と文書IDを紐付ける。表の途中を切らない方法、重なり量、見出しのみの資料の扱いは評価で決める。ページ番号は現行Markdownで保持されているとは限らないため、まず本文位置・見出しを根拠とし、存在しないページ番号を表示しない。

**最初はキーワードとの併用（hybrid）を比較する。** キーワード側と意味側の候補を同じ企業/期間/有効版の条件で取得し、順位を使って統合する案から試す。異なる得点をそのまま加算せず、統合前後を比較する。同一資料の複数小片は文書単位にまとめ、最も関連する原文を返す。`増配` と `減配`、決定と検討中、実施と中止などを近い文章として取り違える可能性を評価に入れる。完全な語句一致を優先できるモードを残し、類似度を確率や確実性として表示しない。

| 比較 | ローカルembedding | 外部embedding API |
| --- | --- | --- |
| 例・一次資料 | [multilingual-e5-smallのモデルカード](https://huggingface.co/intfloat/multilingual-e5-small/raw/main/README.md)。日本語を含む多言語、384次元。入力は最大512トークンで切られ、検索文と本文に所定の接頭辞が必要 | 例として [OpenAI embeddings](https://developers.openai.com/api/docs/guides/embeddings) / [text-embedding-3-small](https://developers.openai.com/api/docs/models/text-embedding-3-small)。本文と検索文から数値表現を返す |
| 費用 | 1回ごとのAPI課金はないが、CPU/GPU時間・RAM・モデル保存・更新作業が必要。nuc7での時間/メモリは未測定 | 入力トークン（モデルが数える文字列の単位）で課金。上記smallのモデル資料は確認時点で100万トークンあたり$0.02。初回索引・更新・検索文・再索引分を合算。為替・税・ホスト費用は別 |
| データ送信 | モデル取得後の推論を端末内で完結させる構成が可能。初期モデルのダウンロード先・テレメトリ有無は導入時に確認 | 公開本文だけでなく検索語も送られる。検索語に利用者の関心や非公開情報が入る可能性がある。保存先のベクトルDBを外部化することとは別の選択 |
| 依存・運用 | モデルと辞書、推論処理系の固定が必要。モデルカードはPython系の実行例。Node用変換形式/ランタイムを使うなら互換性・ライセンス・品質を別途確認 | 認証、ネット接続、レート制限、障害・再試行、料金管理、モデル終了への対応。SDK利用は選択肢であり必須ではない |
| 更新・再索引 | 内容変更分だけ再計算。モデル/正規化/分割方式変更では原則対象全体を再索引し、旧版と混ぜない | 同様。再試行や再索引も費用見積に含む。APIが落ちてもキーワード検索を使える構成にする |
| 判断 | 小さな評価集合で先に実測する候補。ローカルなら高精度・高速という保証はない | ローカルより精度・速度・運用負担の実益がある場合に比較。今回は送信・認証追加・課金をしない |

費用の計算法は `（初期本文＋更新本文＋検索文＋全再索引）の入力トークン合計 ÷ 100万 × 単価`。仮に初回1000万トークンなら上記単価では$0.20だが、これは架空の計算例で、実資料の総量や月額見積ではない。分割の重なり、失敗時の再送、ストレージ・検索計算は別途積み上げる。ローカルも同じ量について処理時間、最大RAM、索引サイズを記録して比較する。

外部送信条件はサービスごとに異なる。OpenAIの資料ではAPI入力は明示的な共有選択なしには学習利用されず、embeddingsの通常の不正利用監視ログ保持は30日、アプリ状態保持はなしとされる。ゼロ保持が既定という意味ではなく、実際の契約・設定は採用時に確認する。[データ管理の一次資料](https://developers.openai.com/api/docs/guides/your-data)

ベクトル保存先も未選定。小規模ではローカルで全候補との距離を計算する比較基準から始め、件数/時間で必要ならSQLite拡張や専用索引を検討する。FTS5はベクトル索引ではない。モデル導入だけでDB置換やDuckDB追加を正当化しない。

### 8.5 保存済み本文・訂正削除・根拠表示の共通設計

SQLiteの開示レコードと保存原本を正とし、検索索引はそこから作り直せる派生データとする。現行の本文がnullならタイトル/会社名だけで検索し、「本文未抽出」と表示する。PDF取得失敗、変換失敗、抽出成功、索引待ち/失敗を区別し、意味検索を導入しても本文欠落は埋まらないことを示す。画像だけの資料にOCRが必要かは未決定で、まず検索漏れとして数える。

提案する索引の管理情報は、文書ID、小片IDと原文位置、本文の指紋、抽出器/正規化/分割/モデルの版、索引世代、処理状態。すべてを第1段階から追加するのではなく、採用方式に必要なものだけ持つ。幅や空白を揃えた検索用文と表示用原文を区別する。

- 表題・本文・URL変更時は該当索引を更新し、古い小片を残さない。モデル応答が遅れても古い本文版の結果を現行版へ書き込まない。
- 同一IDの更新と別IDの訂正資料を区別する。別IDの訂正資料は独立して検索可能にし、根拠なしに自動統合しない。
- 削除を信頼できる情報で確認した場合、現行検索対象から外し、保持方針に従って履歴を区別する。原本の物理削除を自動化しない。単なる一覧消失・404から削除を推測しない点は4.4を維持する。
- 索引作成に失敗しても正のレコードを消さず、再実行可能にする。更新中は旧世代で継続し、整合した新世代に切り替えるか、未索引であることを明示する。再構築前後の文書ID・件数・結果を比較する。
- 検索結果は当たった項目/検索方式、原文抜粋、会社・コード、公開日時、元URL、利用できればローカルPDF、本文と索引の状態を返す。意味検索では生成した説明を根拠の代わりにしない。

### 8.6 評価用クエリと採否の決め方

以下はユーザーの実際の検索履歴ではなく、用途を具体化する仮例。実装前に見つけたい開示例を集め、期待する文書ID/原文箇所・関連性・除外条件を人が記録する。今回は実データを文書に持ち込まず、評価集合そのものの作成とモデル試験は未実施。

| 仮の検索 | 評価する意味 | 検索できてはいけない例・境界 |
| --- | --- | --- |
| `配当 増額` / `増配 OR 復配` | AND/OR、タイトルと本文をまたぐ一致 | ANDで片方しかない資料、指定期間外 |
| `"自己株式取得"` | 連続フレーズ | 離れた位置の「自己株式」「取得」だけで完全一致扱いしない |
| `配当` / `取得` | 日本語2文字 | trigram化で従来の結果が消えない |
| `Ｍ＆Ａ` と `M&A`、`ＡＢＣ` と `abc` | 文字幅・大小の正規化 | 原文表示やコードを破壊しない |
| `自己株式取徳` | 誤字候補を示す | 訂正した検索語を隠さない。コードの誤入力を別企業へ自動修正しない |
| `自社株買い` | 同義表現/意味検索 | 取得と処分・消却を一律同義としない |
| `株主への還元を増やす発表` | 語が一致しない関連開示 | 減配・中止・検討段階を決定と混同しない |
| 企業指定＋JSTの1日 | 全方式で同一filter | 別企業、前日/翌日境界が漏れ込まない |
| 本文にだけある架空語、本文null、訂正後資料 | 本文の有無・索引鮮度 | nullを「該当開示なし」と断定しない。旧抜粋を最新として返さない |

受入は、まずこの種類を含む20〜30クエリ程度を仮目標とし、実際に探したい開示例を反映して固定する。方式の調整用と最終確認用を分け、同じ例に合わせ込んだだけの改善を避ける。候補方式の上位結果を合わせて人が確認し、未知の関連資料を不正解と決め付けない。評価対象集合内の結果と、全TDnetに対する網羅性を分ける。

- 正確性：AND/OR、フレーズ、短語、記号、企業/日付filter、更新/削除は合成データで期待どおりになることを必須とする。
- 見つけやすさ：上位10件の適合率（どれだけ目的に合うか）、既知の関連資料の回収率、最初の正解順位、見つからなかった理由をクエリ群別に比較する。初期基準は現行部分一致。第2段階は第1段階、第3段階は第2段階との改善を見る。
- 採否：意味検索でしか見つからなかった有用な開示が確認でき、正確な語句・企業/日付条件を損なわないこと。改善がなければ第1/2段階で止める。精度の数値閾値は実例評価前に合意し、測定後に都合よく変えない。
- 運用：同じ評価集合で応答時間の中央値/遅い側、最大RAM、初回/差分/全再索引時間、容量、外部費用を記録する。対象件数・許容待ち時間・月額上限は未決定で、架空の性能目標を達成したとは扱わない。

初期の利用面はライブラリ/CLIを仮定する。静的Webは現在JSONだけで完結するため、サーバ側のSQLite検索はそのまま使えない。第1/2段階の共通検索仕様をWebへ反映する案と、ブラウザでの索引・モデル配布、検索用サービスを設ける案を容量/保守負担で比較する。どれも今回採用・公開しない。外部APIキーを静的Webに含めない。

## 9. 実施順と受入条件

検索改善は **評価集合と仕様 → 第1段階 → 第2段階 → 第3段階の比較・採否** の順に行う。評価集合設計と、下表の取得保守は並行して進められる。全ての取得保守完了まで検索仕様の検討を待つ必要はないが、本文欠落と索引の状態を隠して検索精度を評価してはいけない。各実装段階の受入は8.6と下表を併用する。

| 順序 | 作業 | 完了を判断する条件 |
| --- | --- | --- |
| 0 | 検索仕様・評価集合と、取得条件・自動化状態の確認 | 8.6の仮例を見つけたい開示例へ具体化する。現行取得元、保証しない範囲、100/1000件の上限、実在する入口を説明できる。8月以降の運用状態は証拠付きで確認するか未確認と残す |
| 1 | 失敗件数と再処理、入力検証 | 合成データで3回失敗後も明示的再処理から復旧できる。最新一覧外の保存済み失敗IDを扱える。一部失敗と全成功をCLI/ライブラリで区別できる。不正な日付・件数・並列数を拒否し、正常な別資料を失わない |
| 2 | 原本保存と抽出の分離 | 変換失敗でも取得済み原本を保持。本文保存済み＋PDFなしの状態から後保存できる。保存失敗を成功と表示しない。再変換で不要な再ダウンロードをしない |
| 3 | 日付・コード・重複の境界 | JSTの開始直前/開始/終了直前/翌日開始を一時DBで確認。英字コード・4文字末尾0・5文字コードを保つ。同一IDが同じ応答に2回あっても原本取得1回・DB1行。時差の異なる端末でも意図した表示 |
| 4 | 通信・変換の保守と独立テストCI | HTTPモックで429の待機、5xxの有限再試行、404の扱い、時間上限を確認。変換タイマーを成功・失敗時に解放。中止できない処理の限界を記録。テストCIは本番取得・公開を呼ばない |
| 必要時 | 取得範囲の確認とメタデータ更新 | 上限に達した応答を完全取得と表示しない。`total_count` の意味を提供元資料等で確認してから比較。表題が変わった同一IDを本文の不要な再解析なしで更新。別IDの訂正資料を消さない。削除状態を推測しない |

終了条件は、必要な開示を意図した語・条件・言い回しで探せ、原文で確かめられること。あわせて検索範囲・本文欠落・失敗を把握でき、必要な原本を再処理できること。ベクトル検索の採用自体を成功条件にはしない。
